# TradeFlow Java 面试问答

## 一分钟介绍

“TradeFlow 是我从零实现并部署到公网的交易履约平台。后端使用 Java 21、Spring Boot、Spring Security、JPA 和 MySQL，前端使用 Vue 3。项目重点不是普通 CRUD，而是支付回调幂等、订单状态机、库存乐观锁和 Outbox 可靠事件。面试官可以用演示账号实际触发支付、预占库存和状态流转，数据持久化在云 MySQL。”

## 高频问题

### 为什么只做“先查再写”不能保证幂等？

并发请求可能同时查到不存在，再分别写入。应用层检查用于快速返回，`event_id` 唯一索引才是最终防线；项目还锁定订单，保证同一订单的支付状态串行更新。

### 乐观锁解决什么问题？

多个操作同时读取同一 SKU 后预占库存，后提交者可能覆盖先提交者。`@Version` 把版本号加入更新条件，版本不一致就抛出冲突，调用方刷新后重试。

### 为什么使用 Outbox？

直接“更新订单后发送 MQ”存在数据库成功但消息失败的双写问题。Outbox 将业务数据和事件放进同一本地事务，后续 Publisher 可重试投递。演示没有虚构已部署 Kafka。

### 为什么状态机放在服务层？

订单规则属于业务约束。集中在服务层可以让 REST、批处理或消息消费复用同一规则，并把校验和写入放进事务。

### 项目怎么扩展？

先增加 Micrometer 指标和压测，再引入 Redis 缓存热点查询、Kafka/RocketMQ 投递 Outbox、订单历史归档和读写分离。所有演进都以真实瓶颈为前提。
