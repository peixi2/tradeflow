# TradeFlow Java 面试问答

## 一分钟介绍

“TradeFlow 是我从零实现并部署到公网的交易履约平台。我没有把重点放在商品页面，而是选择交易链路最容易出错的三个位置：支付重复回调、库存并发预占和业务状态与事件双写。支付链路通过 event_id 唯一约束、订单行锁和本地事务实现幂等闭环；库存用版本号发现并发覆盖；订单状态和 Outbox 在同一事务提交。线上有 28 条订单和完整事件数据，面试官可以实际重复回调、预占库存并观察状态变化。当前 Outbox 只保证可靠落库，我不会声称 Kafka 已经部署。”

## 高频问题

### 为什么只做“先查再写”不能保证幂等？

并发请求可能同时查到不存在，再分别写入。应用层检查用于快速返回，`event_id` 唯一索引才是最终防线；项目还锁定订单，保证同一订单的支付状态串行更新。

### 唯一约束和订单行锁是不是重复设计？

不是。唯一约束约束的是“同一个支付事件只能记一次”，订单行锁约束的是“同一个订单的状态判断和更新不能交错”。两个不同的事件 ID 仍可能指向同一订单，只靠事件唯一键无法串行化订单更新。

### 为什么在事务里使用 saveAndFlush？

普通 `save` 可能延迟到提交时才执行 SQL。`saveAndFlush` 让支付流水的唯一约束尽早触发，后续状态更新和 Outbox 写入不会建立在一个尚未验证的支付事件上。它不会提前提交，冲突时整个事务仍然回滚。

### 如果支付流水已存在，但订单状态没有更新怎么办？

在当前实现中，支付流水、订单状态和 Outbox 位于同一事务，正常情况下不会只提交其中一部分。如果数据库之外存在人工改数或历史脏数据，需要增加对账任务，按支付流水与订单状态生成差异清单，而不能靠重复回调盲目修复。

### 乐观锁解决什么问题？

多个操作同时读取同一 SKU 后预占库存，后提交者可能覆盖先提交者。`@Version` 把版本号加入更新条件，版本不一致就抛出冲突，调用方刷新后重试。

### 为什么库存不用悲观锁或 Redis 分布式锁？

当前场景冲突概率低，乐观锁不需要长期占用数据库锁，也不引入 Redis 锁续期、误释放和数据库事务一致性问题。若压测发现热点 SKU 冲突率很高，我会优先评估带条件的原子更新 SQL，例如 `reserved = reserved + ? where stock - reserved >= ?`，而不是先增加分布式组件。

### 为什么使用 Outbox？

直接“更新订单后发送 MQ”存在数据库成功但消息失败的双写问题。Outbox 将业务数据和事件放进同一本地事务，后续 Publisher 可重试投递。演示没有虚构已部署 Kafka。

### Outbox 是否等于消息一定送达？

不等于。当前只保证事件不会在业务提交时丢失。还需要 Publisher 扫描、Broker 确认、失败重试、滞留告警和消费者幂等，才能形成端到端的至少一次投递链路。`PENDING` 只是待投递状态。

### 为什么状态机放在服务层？

订单规则属于业务约束。集中在服务层可以让 REST、批处理或消息消费复用同一规则，并把校验和写入放进事务。

### 你如何证明项目不是只做了页面？

可以现场对同一支付事件提交两次，观察第二次返回 `duplicate=true`；尝试把已完成订单退回 `PAID`，接口会拒绝；预占库存后可以同时看到订单状态、SKU 预占量和新增 Outbox。仓库中的集成测试自动覆盖前两个关键路径，公网健康检查同时访问数据库。

### 项目怎么扩展？

先采集支付重复率、事务耗时、乐观锁冲突率、慢查询和 Outbox 滞留时间，再根据指标演进。明确需要异步集成时增加 Publisher 与 Kafka/RocketMQ；读压力和历史数据增长成为瓶颈时再做缓存、归档或读写分离。扩展顺序由观测数据决定，而不是按技术栈清单决定。
